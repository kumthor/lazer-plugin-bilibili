# v0.4.3 — 新 UP 主主页不再加载失败

宿主打开任意 UP 主页固定调用 `artistSongs(limit=100, offset=0)`。v0.4.2 在这个调用上一律返回 `408`，界面显示「插件请求失败，请重试或更新插件」——所以表现得像是「只有没打开过的 UP 主页失败」（打开过的命中宿主缓存）。

## 根因

**不是接口失效，不是登录，不是 WBI 签名，也不是宿主返回的 HTTP 408。**

用真实两页响应（`code=0`、各 50 行、各 50–64 KB）做 httpHandler 后逐层剥离，定位到映射阶段：

| 变体 | 改动 | `limit=100` |
|---|---|---|
| 基线（v0.4.2 等价代码） | — | **408** |
| `no_map` | 不构造歌曲模型 | 通过 |
| `decode_only` | 只解码不映射 | 通过 |

两页解码只花掉 250k 指令预算的一小部分；**预算几乎全被 `util.clean_title` 吃掉**。它对每行标题逐字节 `string.sub` 塞进 table，再跑五遍 `M.replace` 解实体——一行 60 字节标题约 150 条指令。真机投稿页每行 38 字段、标题最长 60 字节，映射到第 **86–95 行**就撞满预算。

二分「最多能映射多少行」：

```
baseline         = 85 / 100
clean_title_fast = 100 / 100   ← 只加这一条
no_duration      = 95 / 100
no_artist        = 100 / 100
```

## 修法（一处）

`bili/util.lua` 的 `M.clean_title`：标题里**没有 `<` 也没有 `&`** 时直接 `M.trim` 返回。

语义不变的依据：没有 `<` 时逐字节扫描的输出就是原串；没有 `&` 时五遍实体替换全是恒等变换。带任一字符时走原路径——真机投稿里 188 条有 13 条标题带 `&`（如「单人&多人合作」「UP&UP 联机」），它们仍按原逻辑处理。

## 修复后的真机读数

```
mid=7000003  limit=100 offset=0/100  -> 100 + 88 行，reachable=188，零 408
mid=7000004  limit=100 offset=0..800 -> 每页 100 行，reachable=900，零 408
```

单页 439–1232 ms。

## 测试补上了真实覆盖缺口

`limit=100` 的契约测试此前用 6 字段短行（`_bulkVlist`），真站每行 38 字段、标题最长 60 字节、部分标题自带 `&`。轻量行测出的「100 行全绿」不能代表真机能过。

新增 `_realArcMode` 与三条断言（**137/137**，原 134 条一条不减）：

- **T11#01**：`limit=100` 在真实两页响应上返回 100 行，首/末 id、`durationMs`、作者名、标题清洗逐字断言
- **T11#02**：`offset=100` 给出剩下 88 行且与首页零重叠；`offset=188` 是空页不是错误；空页不毒化游标
- **T11#03**：快路径语义不变（`<em>` + 实体仍正确剥离解码）

真实响应原样入库为 `test/fixtures/space_arc_real_p1..p5.json`（等字节长度、账号标识已脱敏、字段成本未变）。

**负向控制**：删掉快路径跑同一份契约文件，`T11#01`/`T11#02` 精确变红、`T11#03` 仍绿——成本断言会红，语义断言不会，两条各自承重。

## 明确没做的事

- **没有把页长夹到 50**：宿主按「返回行数 >= limit」判 `hasMore`，50/100 会被读成「没有更多投稿」，第 51 条起永远不可达。
- **没有把异常吞成空列表**：会把插件故障伪装成「这个 UP 没有投稿」。
- **没有碰** `artistDetails`／`parse_duration`／`models.artist`／通用 pager。
- **已知遗留**：宿主 `artistDetails` 仍未用 `try` 包住 `artistSongs`。修好成本后它不再是故障放大器，但任何 `artistSongs` 异常仍会让整页显示「加载失败」——那是宿主侧的问题，不在本版范围内。
