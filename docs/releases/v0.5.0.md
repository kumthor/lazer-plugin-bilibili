# v0.5.0 — 首页「为你推荐的新发行」换源：从榜单到发布时间

v0.4.6 的首页专辑架是**榜单的同义词**，而榜单不新。

| 现象 | 实测 |
| :--- | :--- |
| 「不必按排行榜来」 | `album_candidates` = `popular_rows()` + `chart_raw("3")`，两者都过 `pid_v2 == 1003` |
| 「排行榜不新」 | `ranking/v2?rid=3` 97 行，`pubdate` 中位 **14487 小时 = 603 天**，`<24h` **0/97** |
| 「除了音乐」 | `popular` 音乐区 **0/20**（4 页合计 1/80），架子实际内容几乎全来自 `rid=3` |
| 「更新推荐」 | `album_cache.wide` TTL 6 h，而候选池一天只变 97 条 |

## 换到哪个源（四个候选里排除了三个）

| 源 | 新（`<24h`） | 多元 | 热度 | 分区可过滤 | 结论 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `ranking/v2?rid=3` | **0/97**，中位 603 天 | 仅音乐区 | 有 | `pid_v2` | 不新 |
| `popular` | 14/20，中位 18.9 h | **音乐 0/20** | 有 | `pid_v2` | 单一，只能做辅助 |
| `newlist` | 是 | 一级 rid | 有 | 粗 | **`-412 request was banned`**，带有效签名与真实 cookie 仍被拒，而同一秒 `popular`/`ranking`/`view` 都是 200 |
| `rcmd` 推荐流 | **3/67**，中位 302 h | 天然混排 | 有 | **行内无任何分区字段** | 不新，且无法筛选 |
| `search?order=pubdate` | **30/30**，中位 1.3 h | 按词 + `typeid` | `play`/`like`/`favorites` | `typeid` 66 字段 | **采用** |

`rcmd` 的行只有 26 个字段，**没有 `tid`/`tname`/`pid_v2`/`videos`**，插件只能接受它推什么；67 条里「适合听」的占 16/67。

## 六词 × 一页，映射前先过滤

```lua
local FRESH_WORDS = { "有声书", "公开课", "讲座", "鬼畜", "歌切", "纯音乐" }
local FRESH_PAGE_SIZE = 20   -- 不是 ps=50：那解码量是现状 2.22×
```

`page_size` 上限是 50（`100` 回 `-400`），但真正的约束是**解码成本**。T9/R25 记的那道墙量的是**被映射**的行数，而这个 op 只映射 16 格——过滤发生在 `song`/`album` 映射之前。

## 「新」优先于「纯热度」

刚发布的行 `play ≈ 0`，若按热度在整窗排序只会再选出「旧而热」的内容。所以先攒窗口（6 词 × 20 行 = 120 行 / 9.1 h），再在窗口内排序。

热度公式取 `play + like*10`，依据是 300 行样本的分位：

```
play                p10=0   p50=14  p90=287  p99=1798  zeros=53/300
like/play           p10=0   p50=0.04 p90=0.67 p99=2.0   zeros=97/300
play+like*10        p10=1   p50=50  p90=362  p99=2371  zeros=30/300
```

单用 `play` 有 53/300 是 0、`like/play` 有 97/300 是 0，都会把大半个窗口压成一个不可分的桶。加法而不是 `table.sort`：比较器闭包在 97~100 行上已经把 `homeFeed` 推过 250k 预算直接 408。

## 分区白名单是硬过滤，关键词只负责「找新」

`order=pubdate` 下关键词与主题相关性极弱——「有声书」的前排出现 T1 电竞、两性科普。所以 `typeid` 做真正的主题决定：

```lua
LONG_TIDS  = 195 动态漫.广播剧 / 208 校园学习 / 228 人文历史 / 124 社科 / 201 科普 / 207 财经
SHORT_TIDS = 31 翻唱 / 130 音乐综合 / 59 演奏 / 29 音乐现场 / 193 MV / 30 V家 / 26 音MAD / 22 鬼畜调教 / 216 鬼畜剧场 / 126 人力V
```

`21 日常` 被有意排除：它是所有词的干扰源，白名单命中里占 64/141。

## 两条通道，因为一个时长阈值服务不了两端

鬼畜中位 67 s、听书中位 19179 s，差 286 倍。「≥10 分钟」会把鬼畜与歌切全部滤掉，「按分区」会把听书全部滤掉。所以 16 格按 **3:1** 交错（12 长 + 4 短），某通道不足时按权重顺序补位，不循环复用同一行。

## 卡片第二行：`分区 · 时长`

宿主的货架标题硬编码、`Album` 没有 `duration` 字段、卡片只有两行字（标题 + `album.artist`），所以分区与时长只能进 `artists[1].name`。

**超过 24 h 的时长按数据缺陷处理**：120 行里 7 行超过，最长 14018:40 = 9.7 天，读起来全是连载小说或直播回放被登记成单稿。这些行照常上架，只是不印时长。注意 B 站的 `duration` 是 `MM:SS`、分钟可以超过 60，`233:38` 是 3.9 小时而不是 233 小时——判超限必须按累加后的秒数。

## 两个货架从此是两套候选集

`homeFeed.albums` 读新鲜源；`albums()`（浏览页容器货架）仍读「热门 + 榜单原始行」。语义不同：前者是「推荐现在能听的」，后者是「找一个多 P 合集打开」。

共用的一条教训仍然成立：**408 的成因是映射时机，不是行数**。

## 验证

- 契约测试 **156 条**（v0.4.6 的 140 条一条不减，新增 16 条）。
- 负向控制 5 条全部按预期变红并还原：白名单加回 `21` → `T15#04/#05`；取消 3:1 交错 → `T15#01/#03/#06/#07`；`album.id` 写成 `bvid:cid` → `T15#02/#06/#10/#13`；热度改单 `play` → `T15#06`；超 24 h 不判上限 → `T15#10`。
- 打包 15/15 逐字节一致，安装 15/15 md5 一致。
- 真机：首页货架出现「有声书 / 讲座 / 鬼畜 / 歌切 / 纯音乐」等混排内容，不再是清一色音乐区榜单。

## 已知代价

- 单通道候选薄：`ps=20` 时白名单后长/短各约 25 条，需要 12 长 + 4 短，余量 2.1× / 6.3×——够用但薄。
- 某个词的新内容若全落在白名单外，这个词就白跑一次请求。
