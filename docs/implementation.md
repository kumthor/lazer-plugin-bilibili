# 实现说明：宿主约束与踩坑记录

本文件记录把 B 站接口重写成 Lazer Lua 插件时，**实测**得到的宿主约束与由此产生的实现选择。所有结论都来自在真实发行版宿主里跑出来的行为，不是推测；遇到反直觉的地方都注明了成因。

---

## 1. Lua 运行时是残版 5.3

宿主用 `lua_dardo_plus` 解释 Lua，并裁掉了大量标准库与语法能力。

| 项目 | 实测行为 | 应对 |
| :--- | :--- | :--- |
| `io` / `os` / `package` / `debug` / `dofile` / `load` / `utf8` | 全部为 `nil` | 时间只能用 `host.now()`；无 `utf8.len` |
| `#s`（字符串长度运算符） | `attempt to get length of a string value` | 一律用 `string.len` |
| `%d` `%a` `%s` `%w` `%x` 等模式类 | 全部失效（返回 `nil`） | 用 `[0-9]` 这类字符集替代 |
| 捕获组 `(…)` 与 `%1` 反向引用 | 失效 | 不靠捕获组提取，改纯文本扫描 |
| `gsub` 第三参数为 function / table | 抛 `bad argument #3` | 只用字符串替换形式 |
| `find(s, pat, 1, true)` 纯文本模式 | 正常 | **主力解析手段** |

另有一条容易踩的：字符串在本运行时是 UTF-16 码元序列而非 UTF-8 字节，所以清洗一律按整段 `gsub` 处理，不做字节切片。中文字符的 `string.len` 结果等于字节数 / 3。

## 2. 指令预算 250 000 / 次调用

`invoke()` 通道每次调用有 250 000 条指令预算，超了抛 `408` 并**重建整个 Lua VM**（所有全局状态清零）。

- 逐行解析 300 行 LRC 就要 408 条指令量级，所以**不在 Lua 里拼 LRC 字符串**：歌词只返回结构化的 `lines[]`（`{text, startMs}`），时间轴由宿主合成。
- 搬运字幕能扛约 5 600 行；加 3 次 `gsub` 清洗后上限降到约 3 600 行，因此把字幕行数闸门定在 **1200 行**（3 倍余量）。

## 3. 只有 14 个 host API

v2.0.210 提供：`json_encode` / `json_decode` / `now` / `url_encode` / `random_hex` / `cookie_compact` / `cookie_field` / `cookie_merge` / `crypto` / `http` / `websocket` / `websocket_server` / `storage_get` / `storage_set`。

更新版本的源码树里出现的 `url_decode` / `log` / `sleep` / `timer` / `http_json` 等**不在**这个版本内，实现中一律不用。缺 `sleep` 意味着 412 风控只能返回错误让用户重试，不能自动退避。

`host.http` 的行为补充：

- 强制 HTTPS，非 https 直接 `Network permission denied`。
- 目标域必须精确匹配 `manifest.json` 的 `permissions.network`，或以 `*.` 开头的子域规则。
- `set-cookie` 需要自己从响应头读出来再合并（`http.absorb_set_cookie`），扫码登录正是靠这一步拿到登录态。

## 4. 返回值的类型桥接

Lua table 只有在键为连续整数 `1..N` 时才会被桥接成 Dart `List`；一旦混入字符串键，整张表变成 `Map`。宿主对列表型 op（`favorites` / `playlistSongs` / `artistSongs`）会做 `raw is! List` 检查，不满足即抛 `invalid payload`，界面整页报错。

所以列表型方法**必须返回纯数组表**，分页信息通过入参控制、不夹带在返回值里。

## 5. 三个真机才暴露的 bug

以下三个问题在离线测试里都过，只有真机才现形——记下来是因为它们的形态很有代表性。

### 5.1 扫码二维码渲染成废码

插件原本把二维码信息作为 Lua table 返回（`{hint=…, url=…}`）。宿主 2.0.300 的源码里有 `if (raw is Map)` 分支取 `raw['url']`，但**发行版 2.0.210 把 Lua table 桥接成非 Map 对象**，于是落到 `raw.toString()`，最终编码进二维码的是整个 table 的字符串，B 站 App 判「不支持的二维码」。

修复：`qr_url` 直接返回**纯 URL 字符串**。两个宿主流行版都走 `toString()`，行为一致。另外 `from` 参数必须补成 `main_web`，否则 App 侧同样判废码。

### 5.2 UP 主页「资料加载失败」

两个独立原因叠加：

- `/x/space/wbi/arc/search` 强制要求 `wts`，缺了必返 `412`。WBI 签名统一注入 `host.now()` 毫秒值即可。
- 宿主会调用 `artist` / `artistAlbums` 两个 op，早期实现没提供就直接报 unsupported。补齐后 `artist` 走 `/x/web-interface/card`，取不到时回退占位而不抛错。

### 5.3 评论正文为空

`/x/v2/reply` 的 `content` 是**对象**，正文在 `content.message`。早期代码把 `content` 当字符串取，拿到整个 table 再 `tostring` 成空串。修复时先判类型：table 取 `content.message`，字符串直接用，再回退 `item.message`。

对应的 fixture 也从「字符串」改成真实的嵌套对象结构——否则 fixture 会把 bug 掩盖成假阳性。

## 6. 歌词：为什么选站内字幕而不是第三方曲库

最初方案是用标题去 `lrclib` 精确检索，实测 6 个真实曲目**全部 0 命中**。三个叠加原因：

1. B 站标题是「歌手《曲名》+ 一堆频道后缀」的形态，直接送精确短语检索必然落空。
2. 即使清洗后命中，第三方曲库歌词与该视频的**时间轴也对不上**（曲库版时长与视频时长不同）。
3. 宿主会把空答复落盘成 `pureMusic:true` 的空壳并缓存，后续连插件都不会再调用。

改用视频自带的 `ai-zh` 字幕（`view` → `player/wbi/v2` → 字幕 CDN JSON 三步）：与视频同源，时间轴零误差，实测 6/6 命中且都在 1 秒内。`lrclib` 降级为极少数补充，且带时长闸门——对不上就干净返回空，不硬凑。

`/x/player/wbi/v2` 而不是 `/x/player/v2`：同一个 bvid 前者返回字幕列表，后者常常为空。

## 7. 时长字段：列表接口各不相同

不同接口给时长的字段名不一样，映射时必须逐条回退：

- `/x/web-interface/view` → `duration`（秒，数字）
- `/x/space/wbi/arc/search` 的 `vlist` → **`length`**（`"MM:SS"` 字符串），没有 `duration`
- 搜索/热门/排行 → `duration` 或 `length` 都可能出现

统一策略：`duration` → `length` → `duration_seconds` 依次回退，全部交给同一个 `parse_duration` 转毫秒。**不要**在拿到秒数后再乘一次 1000。

## 8. 收藏夹封面

`/x/v3/fav/folder/created/list-all` 返回的 folder **没有 cover 字段**（实测为空），只读 `cover`/`pic` 就只能画灰色占位符。修复：取不到时用 `/x/v3/fav/resource/list?ps=1&pn=1` 第一个视频的封面回填；资源列表本身为空则返回 nil，不编造。

## 9. 分页聚合

宿主问 100 行时，如果插件只给 50 行，宿主会判定为末页直接停住。`catalog.lua` 里的 `collect(load, limit, offset, cap, max_hops)` 聚合器负责：页内偏移、短页即末页、最多 6 跳。实测 684 条 UP 投稿 8 次调用读全，`offset` 越过总数后返回 0 行、`hasMore=false`。

## 10. 分页器：为什么不能只"请求一页、短页即结束"

宿主对列表型 op 的调用方式是 `hasMore = 返回行数 >= limit`、`nextOffset = offset + 返回行数`。这套算术把三件事变成了硬契约：

1. **返回短页 = 宣告到头**。所以"读不到"绝不能伪装成"没有了"：预算耗尽又没凑满 `limit` 时，收藏夹与投稿族报可重试错误，不返回短页。
2. **`offset` 必须与行下标同空间**。分 P 列表里空 `cid` 的行无法播放，映射时会被丢掉；**先切片再丢行**会同时造成短页和偏移错位，所以必须先构造可映射行表、再在同一个行空间切片。
3. **远端页长不等于请求的页长**。收藏夹的失效稿件会在服务端被过滤（实测 `ps=40` 回 38 行、`ps=20` 回 19 行），页边界只能按实际取到的行数累计。

### 游标里的两个数字

`/x/v3/fav/resource/list` 在 `pn` 超过末页时同时返回 `medias: []` 和 `info.media_count: 0`。把那个 0 当成权威总数写进游标，之后同 key 的每次调用都会在第一行提前返回——不发请求、不报错、界面空白。

修法是把两个数字分开：

- `total`：只在**非空页**写入，描述"上游说的总数"；
- `proven`：本游标**真实读到**的行数下界。

停止条件用 `proven`，展示用 `total`。评论同理：接口没给 `count` 时留空（宿主读成 0 = 未知），绝不用请求偏移填充。

### 跳页 vs 顺序走

评论页是**严格位置切片**（实测 `pn=1/2/3/4/5/10/20/33/66` 都是 20 行、跨页零重复），所以深 offset 直接算出页号跳过去；收藏夹是短页序列，**不能**跳。分页器因此把跳页做成可选开关，只有评论族打开。

## 11. 请求预算：按族分开，按解码行数计

250 000 指令预算不是按"请求次数"计的，而是按**解码的行数**计的，且行越长越贵。两个结论都来自测量而不是推演：

- **签名族比明文族便宜**：明文族（`reply`/`fav_resource`/`popular`/`ranking`/`view`/`player`）实测在 153–232 次之间被 408 打断；签名族（`search`/`space/arc` 的 WBI 请求）随载荷在 22–75 次之间。两族共用 32 会让 `artistSongs(offset≥800)` 直接把 VM 打挂。现在明文 32、签名 12。
- **`search` 的上限是 35 行，与 `limit` 无关**：把 `limit` 固定为 1、只改每桶行数，90 行通过、100 行 408。旧代码 `cap=50` 让两个桶各解一整页 = 100 行，所以**任何** `limit` 都会 408。

## 12. 多分 P：容器与曲目的分层

B 站的多 P 视频在接口层是一个视频 + 若干 `pages`。直接把它当成一首歌，所有 P 会混成同一首；只取第一 P，则其余 P 永远不可达。

现在的分层是：

```
homeFeed.albums / albums   →  视频容器（行里带 videos 数）
albumSongs(bvid)           →  各 P 的曲目行，id = bvid:cid
song / stream / lyrics     →  按 bvid:cid 取对应 P
```

两个坑：

- **多 P 判定必须读原始行**。`chart_rows` 返回的是已映射的 song 形状，没有 `videos` 字段，用它判多 P 恒为否。
- **每行不要重复计算整视频级的量**。`clean_title(title)`、`clean_title(data.title)`、`image(pic)`、`models.artist(owner)` 都是整视频级的，放进循环会让 60 行就撞 408。提到循环外后离线 160 行通过，页长上限才能提到 100。

## 13. 首页专辑架：候选集与降级

首页专辑架最初恒空。原因不是"没有多 P 视频"，而是候选集只读了热门流，而真机 20 条热门**全是单 P**。

v0.4.4 又修了它的另一半：架上的东西**不是音乐**。候选集当时只按 "多 P" 筛，不看分区，于是游戏、影视、鬼畜类稿件照样上架。现在两层候选都要求 `pid_v2 == 1003`（不是 `tid`——同一个 `tid` 会跨分区出现，`pid_v2 = 0` 也是真实取值），并且音乐区榜单 `rid=3` 自身也要筛：它 97 行里有 11 行属于其他分区。

改成「热门 + 榜单原始行」后还有一个陷阱：**映射时机**。把榜单 100 行映射成 song 形状会 408（预算按解码行数计），只读**原始行**是 6 请求正常返回。所以缓存里存原始行，用到时才映射。

单 P 也从"不上架"改成"上架"：一个 1 首歌的专辑，`songCount = 1` 是真实值。只有 `videos > 1` 的候选才花 `view` 预算，所以 `ALBUM_LIMIT` 只对多 P 候选计数。

榜单**不按 `score` 重排**：97/97 行 `score` 恒为 0，排序是空操作，而 `table.sort` 在 97 行上就会把 `homeFeed` 推过 250k 预算。

降级策略有两条约束：

- 榜单失败只牺牲榜单候选，热门失败照常上抛——热门是首页主内容，不能因为榜单挂了就整页空白；
- **降级结果不写缓存**。写进去的话，一次临时故障会被钉住 6 小时。

## 14. 歌词三态与纯音乐

`minAppVersion` 是 2.0.210，而这个版本会把空歌词答复落盘成 `pureMusic: true` 的空壳，且**该空壳不含 `savedAt`**。较新版本（2.0.300）的 24 h TTL 只在 `savedAt` 存在时生效，所以那个空壳也救不回来——一次空答复等于永久纯音乐。

因此本插件**从不返回空歌词表**：两个源都没有时一律报可重试错误。代价是确认无字幕的纯音乐曲目会一直显示可重试的错误，而不是「纯音乐」；这是当前宿主版本下唯一不产生永久脏状态的选择。

## 15. 测试基座：从"返回了什么"到"宿主会怎么做"

最初 20 条测试全绿，但真机仍然坏——因为测试验证的是"插件返回了什么"，而没验证"宿主拿这个结果会怎么做"。

现在的做法：

- 直接模拟宿主的 `hasMore`、`nextOffset` 与 `all()`，把分页契约变成可断言的对象；
- fixture 使用真站字段与真实末端行为（越界页的 `media_count: 0`、短页、缺 `count` 的非空页）；
- 每个测试独立 VM 与独立存储，消除状态串联；
- 新缺陷先在旧代码上复现红，再验证修复转绿；
- **负向控制**：把关键结构改掉必须让一组断言变红。例如把 `chart_raw` 换回 `chart_rows` 会让五条断言失败，把 `albumSongs` 页长夹回 30 会让页长契约那条失败。没有负向控制的"全绿"证明不了结构承重。
- **fixture 的字段成本必须与真机同量级**。`limit=100` 的 UP 投稿测试曾用 6 字段短行，全绿；而真站每行 38 字段、标题最长 60 字节、13/188 条标题带 `&`，同一份代码在真机 408。真实两页响应现在原样入库（`test/fixtures/space_arc_real_p1..p5.json`，等字节长度，账号标识已脱敏），由 `T11#01`/`T11#02` 直接消费。

## 16. 标题清洗：一个被低估的热点

`clean_title` 要处理搜索结果的 `<em class="keyword">…</em>` 与 HTML 实体。原实现对每个字符串做**逐字节** `string.sub` 扫描塞进 table，再跑五遍 `M.replace` 解实体——因为运行时是残版 5.3，没有 `%b` 以外的模式技巧可用。

单次调用看不出来，100 行一起映射就是灾难：一行 60 字节标题约 150 条指令，250k 预算在真机投稿页上只够 85 行。而宿主打开 UP 主页固定要 100 行。

修法是加一条**语义等价的快路径**：字符串里既没有 `<` 也没有 `&` 时直接 `M.trim` 返回。依据是纯逻辑的——没有 `<` 时逐字节扫描的输出就是原串本身；没有 `&` 时五遍实体替换全是恒等变换。带任一字符时走原路径，行为逐字不变。

这类"热点只在放大后可见"的地方，判断依据不能是"看起来慢"，要能拆开测：把映射、解码分别剥掉跑同一份真实响应，看预算死在哪一层。这里 `no_map` 和 `decode_only` 两个变体都通过，而基线 408，才把嫌疑锁死在映射阶段，再用「最多能映射多少行」的二分把范围收窄到单个函数。

## 17. 专辑名的列预算：为什么必须由插件来裁

宿主用 `maxLines: 1 + overflow: ellipsis` 渲染专辑名（`player_controls_bar.dart:131`、`desktop_now_playing.dart:532`），而且**省略号加在整串末尾**。B 站标题动辄 50 列以上，所以 ` · N P` 后缀会被整段吃掉——专辑行又变回"看不出有几 P"。

因此裁剪必须在插件侧做，并且预算要按**整串**算：

```
ALBUM_LABEL_COLUMNS = 32            -- 标题 + ` · N P` 一起
tail_width = columns(suffix)        -- 宽字符按 2 列
room       = 32 - tail_width
room <= 0  → 只返回后缀            -- 知道"有 100 P"是这个标签的全部意义，
                                    -- 截成 " · 10…" 是错数字
否则        → clip(base, room - 1) .. suffix
```

那个 `- 1` 不是保守：`clip` 的语义是"填满 limit 列，**然后**追加省略号"，省略号自己占 1 列。漏掉它整串就超预算 1 列，而宿主按列宽省略——超 1 列等于后缀被吃掉。这个 bug 是探针量出来的（`evidence/t13/FIT_LABEL_PROBE.log` 的 `outCols=33 > budget=32`），而当时有一条逐字断言**把它的输出钉成了正确答案**。

两个构造点（`models.song` 与 `catalog.album_songs`）必须共用同一个常量，否则同一支视频从列表进与从专辑页进会得到不同的专辑名。

## 18. 留空 vs 写纯标题：宿主队列的合并规则

```dart
// music_platform_state.dart:635
album: entry.album.isEmpty ? updated.album : entry.album,
```

队列条目里的 `album` **非空就不再被覆盖**。所以"先写纯标题、等 `song()` 再改"是走不通的：写进去那一刻播放页就永远停在纯标题上了。

`search` 与收藏夹行拿不到 P 数（真站 0/20、0/19，`videos` 字段不存在），于是只有两条路——猜一个数字（写假信息）或留空。留空让 `hydrate()` 在用户真的按下播放时把它填成带后缀的那一版，而 `_loadCurrentArtwork()` 在每条播放路径上都会被调用（`app_state.dart` 里 6 处）。

代价是宽屏列表那一列专辑名变空白。这不是遗漏，是"让信息出现在用户需要它的地方"的直接结果：宽屏专辑列原本与标题列逐字重复。

## 19. 分 P 数的来源：不猜

| 行来源 | N 取自 | 依据 |
| :--- | :--- | :--- |
| `popular` / `ranking` / `related` / `space.arc` | 行内 `videos` | 实测 20/20、97/97、40/40、有 |
| `view`（`song` / `albumSongs`） | `view.pages` 的条数 | 与 `videos` 一致（3/3 对照） |
| `search` / 收藏夹 | **无**，留空 | 真机 0/20、0/19，字段根本不存在 |

给没有 N 的行补 N 的三条路都量过（`evidence/t14/`）：搜索接口的 66 个字段里没有 `videos`；`bvid=A,B` 逗号批量两个接口都回 `-400`；逐行 `pagelist` 让首屏从 697 ms 涨到 2 681 ms（+2.85×），且 `limit` 上限 100 时线性放大。留空是零额外请求的方案。

顺带纠正一个假设：原以为"20 个 `pagelist` 会撞 250k 预算"。实测 30 次全部通过——真正的 408 边界在**解码多少个字段**，不在发多少个请求。

## 20. 首页货架：为什么榜单不能当"新发行"

`homeFeed.albums` 是首页唯一能给插件的位置（宿主货架标题硬编码，`HomeFeed` 没有额外槽位）。它在 v0.4.x 读「热门 + 音乐区榜单」，而这个组合不是"新"：

```
ranking/v2?rid=3    n=97   pubdate p10=14440.8h p50=14487.8h p90=14700.3h   <24h=0
popular pn=1..4     n=80   <24h=47   音乐区 1/80
```

97 行的 `pubdate` 中位是 603 天，24 小时内 0 条——一个叫「为你推荐的新发行」的区块，内容是一年半前的音乐区排行榜。用户的原话是"排行榜的变化很小而且也不新，没有更新推荐的意味"。

四个候选源的实测：

| 源 | 新（`<24h`） | 多元 | 热度 | 分区可过滤 | 结论 |
| :--- | :--- | :--- | :--- | :--- | :--- |
| `ranking/v2?rid=3` | 0/97，中位 603 天 | 仅音乐区 | 有 | `pid_v2` | 不新 |
| `popular` | 14/20，中位 18.9 h | 音乐 0/20 | 有 | `pid_v2` | 单一 |
| `newlist` | 是 | 一级 rid | 有 | 粗 | `-412` 封禁 |
| `rcmd` | 3/67，中位 302 h | 天然混排 | 有 | **无任何分区字段** | 不新且不可筛 |
| `search?order=pubdate` | 30/30，中位 1.3 h | 按词 + `typeid` | 有 | 66 字段 | 采用 |

`newlist` 的封禁值得单记：带 32 字节 salt、真实 cookie、完整 WBI 签名重试三种组合全部 `-412 request was banned`，而同一秒 `popular` / `ranking` / `view` 都是 `code=0`。它不是全局风控，是这个端点自己的门槛，不适合放在首页冷启动路径上。

## 21. 为什么"新"和"热度"不能同时优化

`order=pubdate` 的第一页全是几分钟前发布的行，`play` 是 0 到 10 的量级；而排序若在整个窗口内按热度做，这些行永远排在最后，等于又回到"旧而热"。

所以是两段式：先攒窗口（词 × 页），再在窗口内排序。窗口大小由**解码预算**决定，不是由理想样本量决定——`ps=30` 十词已经是 498,780 B。

热度公式的选择也是量的：

```
play                p10=0   p50=14  p90=287  p99=1798  zeros=53/300
like/play           p10=0   p50=0.04 p90=0.67 p99=2.0   zeros=97/300
play+like*10        p10=1   p50=50  p90=362  p99=2371  zeros=30/300
```

零值比例决定分辨率：53/300 或 97/300 是零，意味着大半个窗口挤在同一个不可分的桶里，排序退化成"谁先被搜到"。`play + like*10` 把零值压到 30/300，且 p90/p10 = 362。

它必须是**加法**而不是 `table.sort` + 比较器闭包：后者在 97~100 行上已经把 `homeFeed` 推过 250k 预算（`evidence/t12/T01_sort_budget.log`）。

## 22. 一个通道 = 一个分区集合 + 一个准入规则

三条通道的差别不是"时长阈值"，而是**准入规则的种类**：

| 通道 | 准入 | 为什么不能统一 |
| :--- | :--- | :--- |
| long | `typeid` 在白名单 | 听书/讲座的分区是稳定的 |
| short | `typeid` 在白名单 | 鬼畜/歌切同理 |
| asmr | `21 日常` **且** 标题或 tag 带标记；或白名单内自报 ASMR | 71/120 行落在 21，而 21 是最大的干扰源（白名单命中里占 64/141） |

ASMR 是唯一不能只看 `typeid` 的通道，因为它的内容散落在 `日常`（占多数）与几个真实分区（`人文历史` x2、`音乐综合` x1 的跨界实测）。反过来，标记也不能放宽分区门——自报 ASMR 的网络游戏视频不该上架。

「21 + 标记」这条规则之所以成立，靠的是**对照**而不只是命中率：ASMR 词的 21 行 71/71 带标记，非 ASMR 词的 21 行 0/4 带标记。只看前者无法排除"21 里的行本来就都带这些词"这个解释。

## 23. 跨通道去重：为什么 `seen` 必须是共享的

三个通道各自维护 `seen` 时，一条行可以同时满足两个通道的准入：

```
助眠 词 → 搜到 BVxxx（228 人文历史，标题带"助眠"）
          want=asmr + 标记命中 → 归 asmr ✓
文学朗读 词 → 搜到同一个 BVxxx（228 人文历史，无标记）
          typeid 228 在白名单 → 归 long ✓
```

结果是同一条视频在货架上出现两次、带两个不同标签。真机截图直接看到了它（`ASMR · 39:52` 与 `人文历史 · 39:52` 是同一个视频）。

修法是三个通道共享一个 `claimed` bvid 集合，按 `asmr → long → short` 的顺序构建，高权重通道先认领。

值得注意的是**这个缺陷在 fixture 里查不出来**：按通道统计 fixture 的重复 bvid 是 0，因为构造的十页里没有跨界行。它只在真实回包上出现，所以证据是截图与活体探针；`T16#15` 是事后补的回归钉。

## 24. 卡片第二行：一个字符串要同时编码三件事

宿主首页卡片只有两行字（标题 + `album.artist`），`Album` 没有 `duration` 字段。所以"通道 + 分区 + 时长"三件事全压在一个字符串里：

```
ASMR · 1.0h            ← asmr 通道，具体词 + 时长
人文历史 · 15.1h        ← long 通道，真实分区 + 时长
音乐综合 · 2:08         ← short 通道，真实分区 + 时长
人文历史                ← 时长超 24h，按数据缺陷只留分区
```

两条规则是从真机读数里改出来的，不是设计时想到的：

1. **ASMR 槽必须写通道名**。第一版只在线上分区是 `21` 时改写，结果 ASMR 槽与 short 槽在真机上都显示 `音乐综合`——用户看不出"ASMR 占一半"生效了。
2. **不能退回线上分区名**。`21 日常` 在卡片上没有信息量；`音乐综合`/`人文历史` 会与其它通道的标签相撞，而且 `tid=21` 的 `view.tname` 在真站是空串。

v0.6.1 进一步把扁平的 `ASMR` 换成**具体词**（`助眠` / `白噪音` / `哄睡` / `环境音`），判据是位置而不是优先级表：标题里最早出现的标记词胜出，标题没有词时才由 `tag` 决定。61 行里 36 行标题带词、25 行只有 tag——后者正是扁平标签会埋掉的那部分。

## 25. 时长字段的第三种坑：`MM:SS` 里分钟可以超过 60

`duration` 在搜索行是 `MM:SS` 字符串，而 B 站允许分钟位超过 60：`233:38` 是 **3.9 小时**，不是 233 小时。把它当"分钟:秒"直接换算会得到 14 000 小时，进而被"超 24 h 判数据缺陷"的门误杀。

同一批数据里确实有真正的异常：120 行里 7 行超过 24 h，最长 `14018:40` = 9.7 天，读起来全是连载小说或直播回放被登记成单稿。这些行照常上架，只是不印时长。

判超限必须按**累加后的秒数**，不是按字段的位数。
